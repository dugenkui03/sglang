## 生产指标(Production Metrics)

SGLang 通过 Prometheus 提供生产指标(Metrics)。启动服务器时添加 `--enable-metrics` 即可启用。
可以通过以下命令查询：

```bash
curl http://localhost:30000/metrics
```

更多详情参见[生产指标(Production Metrics)](https://docs.sglang.io/docs/references/production_metrics)和[生产请求追踪(Production Request Tracing)](https://docs.sglang.io/docs/references/production_request_trace)。

## 日志(Logging)

默认情况下，SGLang 不记录任何请求内容。使用 `--log-requests` 可以记录这些内容。
使用 `--log-request-level` 可以控制日志的详细程度(Verbosity)。
更多详情参见[日志(Logging)](https://docs.sglang.io/docs/advanced_features/server_arguments#logging)。

可以在运行时(Runtime)调整日志的详细程度：

```bash
python3 -m sglang.srt.managers.configure_logging --url http://localhost:30000 --log-level=debug
```

## 请求转储与回放(Request Dump and Replay)

你可以转储(Dump)全部请求，稍后回放(Replay)，用于基准测试(Benchmarking)或其他目的。

要开始转储，使用以下命令向服务器发送请求：

```bash
python3 -m sglang.srt.managers.configure_logging --url http://localhost:30000 --dump-requests-folder /tmp/sglang_request_dump --dump-requests-threshold 100
```

服务器每收到 100 个请求，就会将这些请求转储到一个 pickle 文件中。

使用 `scripts/playground/replay_request_dump.py` 可以回放请求转储文件。

## 崩溃转储与回放(Crash Dump and Replay)

服务器有时可能发生崩溃(Crash)，你可能希望调试其原因。
SGLang 可以保留近期的请求数据以便回放，并收集 CUDA 设备核心转储(Device Coredump)，用于底层调试(Low-Level Debugging)。

使用 `--crash-dump-folder /tmp/crash_dump` 设置崩溃诊断目录(Crash Diagnostics Folder)。

当 SGLang 处理崩溃时，会将崩溃转储缓冲区(Crash-Dump Buffer)中保留的已完成请求，以及正在处理的请求(In-Flight Requests)，写入 `/tmp/crash_dump/<hostname>/crash_dump_<timestamp>.pkl`。
该文件还包含服务器参数(Server Arguments)和启动命令(Launch Command)。使用 `scripts/playground/replay_request_dump.py` 可以回放该文件。

在 NVIDIA CUDA 环境中，该选项还会在 CUDA 初始化之前设置默认环境变量(Environment Variables)。
这些默认值会启用 CUDA 异常(CUDA Exception)发生时的设备核心转储，并允许 SGLang 在处理崩溃时，为仍在运行的调度器进程(Scheduler Process)触发设备核心转储。
CUDA 设备核心转储会写入 `/tmp/crash_dump/<hostname>/core.cuda.<timestamp>.<pid>`。
显式配置的 CUDA 核心转储环境变量优先生效，包括自定义的 `CUDA_COREDUMP_FILE` 路径。
该选项不会配置操作系统(Operating System，OS)的进程核心转储(Process Core Dump)。

## 术语与生词表(Terms and Vocabulary，学习补充)

| 术语或单词 | 中文释义 | 简明英文释义 |
|---|---|---|
| Observability /əbˌzɜːvəˈbɪləti/ | 可观测性：通过指标、日志等信息了解系统内部的运行状态。 | The ability to understand a system's internal state from the information it produces. |
| Metric /ˈmetrɪk/ | 指标：用于衡量系统状态或性能的数值。 | A numerical measure of a system's state or performance. |
| Verbosity /vɜːˈbɒsəti/ | 详细程度：这里指日志记录的信息量。 | The amount of detail included in output or messages. |
| Tracing /ˈtreɪsɪŋ/ | 追踪：记录请求在系统中的执行过程。 | Recording the path and progress of a request through a system. |
| Dump /dʌmp/ | 转储：将请求或运行状态等数据保存到文件。 | To save data or program state to a file for later use. |
| Replay /ˌriːˈpleɪ/ | 回放：重新执行先前记录的请求或操作。 | To run previously recorded requests or operations again. |
| Benchmark /ˈbentʃmɑːk/ | 基准测试：在给定工作负载下测量和比较性能。 | A test used to measure and compare performance under a defined workload. |
| Crash /kræʃ/ | 崩溃：程序因错误而意外停止正常运行。 | An unexpected failure that stops a program from running normally. |
| Buffer /ˈbʌfə/ | 缓冲区：临时保留数据的存储区域。 | A storage area that holds data temporarily. |
| In-Flight Request | 正在处理的请求：已进入系统，但尚未完成的请求。 | A request that has entered the system and has not yet finished. |
| Device Coredump | 设备核心转储：保存设备执行状态的诊断数据，供底层调试使用。 | Diagnostic data capturing a device's execution state for low-level debugging. |
| Environment Variable | 环境变量：传递给进程、用于配置其行为的命名值。 | A named value supplied to a process to configure its behavior. |
| OS — Operating System | 操作系统：管理硬件资源并为程序提供运行环境的系统软件。 | System software that manages hardware resources and provides an environment for programs. |
