# 4.2 量化键值缓存(Quantized KV Cache)

本文根据 SGLang 量化键值缓存文档翻译；[仓库中的原文](../docs/docs/advanced_features/quantized_kv_cache.mdx)。功能兼容范围按译文对应版本描述，部署时以所用版本为准。

量化键值缓存通过使用更低精度的 FP8 或 FP4，替代默认的 BF16，减少键值缓存(Key/Value Cache，KV Cache)的显存占用。在自回归生成(Autoregressive Generation)过程中，大语言模型(Large Language Model，LLM)缓存已经计算出的键值对，避免重复计算。序列越长，缓存通常占用越多显存。
这项优化主要通过容纳更多词元(Token)，提高系统吞吐量(Throughput)，但不同量化格式可能带来不同程度的准确率下降。

> 性能提醒：如果使用缓存前需要反量化(Dequantization)，而反量化没有与注意力内核(Attention Kernel)融合，推理可能明显变慢。应确认所选注意力后端(Attention Backend)支持相应格式，否则吞吐量损失可能抵消显存收益。

## 支持的格式(Supported Formats)

开放计算项目(Open Compute Project，OCP)定义了两种常见的 8 位浮点格式(FP8)，两者都包含 1 位符号位(Sign Bit)：

| 格式 | 指数(Exponent) | 尾数(Mantissa) | 特点 |
|---|---|---|---|
| E5M2 | 5 位 | 2 位 | 动态范围(Dynamic Range)较大，可达 ±57344，精度相对较低。 |
| E4M3 | 4 位 | 3 位 | 精度相对较高，动态范围较小；原文标注为 ±240。 |

> 译注：E4M3 的范围取决于具体变体。根据编码规则，E4M3FN 的最大有限值为 448，E4M3FNUZ 为 240；±240 不能泛指所有 E4M3 格式。[ONNX 格式说明](https://onnx.ai/onnx/technical/float8.html)

**FP4 格式目前属于实验功能。** OCP 定义了微缩放四位浮点格式(Microscaling FP4，MXFP4)。SGLang 提供两种实验性的 E2M1 缓存量化方案：

- `nvfp4`：NVIDIA FP4，每 16 个数值组成一块，使用 E4M3 分块缩放因子(Block Scale)，以及逐张量全局缩放因子(Per-tensor Global Scale)。
- `fp4_mx_block16`：块大小为 16 的 E2M1 兼容方案，与标准 OCP MXFP4 的块大小 32 有所区别。

## 启用方式(Usage)

启动服务时，通过 `--kv-cache-dtype` 指定缓存的数据类型：

```bash
# FP8 E5M2 缓存
python3 -m sglang.launch_server --model-path deepseek-ai/DeepSeek-R1-0528 --kv-cache-dtype fp8_e5m2
# FP8 E4M3 缓存
python3 -m sglang.launch_server --model-path deepseek-ai/DeepSeek-R1-0528 --kv-cache-dtype fp8_e4m3
# NVFP4 缓存
python3 -m sglang.launch_server --model-path nvidia/DeepSeek-R1-0528-NVFP4 --kv-cache-dtype nvfp4
# 块大小为 16 的 FP4 E2M1 缓存
python3 -m sglang.launch_server --model-path deepseek-ai/DeepSeek-R1-0528 --kv-cache-dtype fp4_mx_block16
```

## SM100 上的原生 NVFP4 方案(Native NVFP4 Recipes)

在 SM100 上，预填充(Prefill)可以直接读取打包存储的 NVFP4，也可以先将其反量化到 FP8 E4M3 工作区(Workspace)。通过 `--prefill-kv-cache-dequant-dtype` 选择运行时反量化的数据类型，SGLang 会选择对应的注意力实现。

```bash
# 预填充和解码均直接使用原生 NVFP4
python3 -m sglang.launch_server \
    --model-path Qwen/Qwen3.5-35B-A3B-FP8 --tp-size 1 \
    --kv-cache-dtype nvfp4 --prefill-kv-cache-dequant-dtype nvfp4 --page-size 16
# 预填充使用临时 FP8 反量化工作区，解码使用原生 NVFP4
python3 -m sglang.launch_server \
    --model-path Qwen/Qwen3.5-35B-A3B-FP8 --tp-size 1 \
    --kv-cache-dtype nvfp4 --prefill-kv-cache-dequant-dtype fp8_e4m3 --page-size 16
```

`nvfp4` 表示预填充直接读取原生 NVFP4 缓存，无须额外反量化。默认值 `auto` 在 SM100 上选择原生 NVFP4，在 SM120 上选择反量化为 FP8 E4M3。两种方案的解码(Decode)阶段都使用原生 NVFP4，KV 数据始终以打包的 FP4 形式存储。
原生方案省去了 FP8 工作区及按词元线性排列的缩放因子副本；FP8 方案同时保留预填充使用的线性缩放因子，以及解码使用的物理缩放布局。

原文列出的要求和兼容范围：

- 原生 NVFP4 预填充要求 SM100、页面大小(Page Size)能被 4 整除、注意力头维度(Attention Head Dimension)能被 64 整除。
- TRT-LLM GenMHA 内部使用 FP8 查询(Query)和输出缓冲区，SGLang 再将输出转换回模型激活值(Activations)的数据类型。
- 支持 `top-k=1` 的 EAGLE、EAGLE3、NEXTN，以及搜索宽度为 1 的 NGRAM 推测解码(Speculative Decoding)；NGRAM 需设置 `--speculative-ngram-max-bfs-breadth=1`。
- EAGLE 系列的草稿工作进程(Draft Worker)使用 `trtllm_mha`；目标校验(Target Verification)在即时执行(Eager Execution)和 CUDA 计算图(CUDA Graphs)中都直接读取物理 NVFP4 缓存。
- 混合使用 FlashInfer 预填充与 TRT-LLM 解码时，SGLang 会将 `--speculative-attention-mode` 解析为 `decode`，使校验不依赖 FlashInfer 的临时反量化工作区。
- SM100 原生路径暂不支持其他推测算法、预填充与解码分离(Prefill-Decode Disaggregation，PD Disaggregation)、分层键值缓存(Hierarchical KV Cache)和 LMCache；SM120 XQA 继续使用该架构专用的线性缩放布局，以及 BF16 查询和输出路径。

## 缩放因子(Scaling Factors)

FP8 量化需要缩放因子完成缓存的量化和反量化。原文说明，目前仅支持逐张量缩放(Per-tensor Scaling)，即每个相关张量使用一个标量(Scalar)缩放因子。

- 从检查点(Checkpoint)加载：预量化模型，例如通过 ModelOpt 处理的模型，可能包含 `k_scale` 和 `v_scale`，框架会自动加载。
- 通过 JSON 提供：使用 `--quantization-param-path` 指定缩放因子文件，格式如下。

```json
{
  "kv_cache": {
    "dtype": "float8_e4m3fn",
    "scaling_factor": {
      "0": {"0": 1.0, "1": 1.0}
    }
  }
}
```

`scaling_factor` 的外层键表示张量并行编号(Tensor Parallel Rank)，内层键表示模型层索引。如果没有提供缩放因子，检查点中也没有，默认使用 `1.0`，可能影响准确率。
对于原文所述的 FP4(MXFP4)方案，分块缩放因子会在量化、反量化过程中按需动态计算，无须为了提供这些因子而使用预量化模型或外部缩放文件。

## 显存收益(Memory Savings)

计入缩放因子开销后，块大小为 16 的 FP4 缓存，理论上能容纳约 BF16 的 **3.56 倍词元**，约为 FP8 的 **1.78 倍**。同样的显存预算因此可以支持更长上下文或更多并发请求。
以原生 `nvfp4` 为例，每个数值需要 `0.5 字节 FP4 数据 + 1/16 字节分块缩放因子 = 0.5625 字节`；BF16 每个数值需要 2 字节，因此理论容量比为 **`2 / 0.5625 ≈ 3.56`**。
SM100 混合方案还需要第二套缩放布局和共享的单层 FP8 预填充工作区，实际容量取决于全注意力层(Full-Attention Layer)数量。SGLang 在计算缓存池(KV Pool)大小时会计入这些辅助缓冲区。

> 译注：原文在此处将 FP4、FP8 的额外开销都描述为“分块缩放因子”，与前文 FP8 仅支持逐张量缩放的表述不一致；具体缩放方式应结合格式和实现确认。

## 对准确率的影响(Accuracy Impact)

FP8 E4M3 通常只带来较小的准确率下降；影响取决于模型架构、序列长度和量化格式，通常 E4M3 的准确率优于 E5M2。FP4 的影响更依赖模型和任务。原文引用多头潜在注意力(Multi-head Latent Attention，MLA)的 [PR #10078](https://github.com/sgl-project/sglang/pull/10078)，以及多头注意力(Multi-head Attention，MHA)的 [PR #12612](https://github.com/sgl-project/sglang/pull/12612)，给出以下初步结果：

| 模型 | 数据集 | KV16 | KV8：FP8 E4M3 | KV4：FP4 E2M1 |
|---|---|---:|---:|---:|
| Qwen3-235B-A22B | gsm8k | 0.9168 | 0.9181 | 0.9186 |
| Qwen3-235B-A22B | aime25 | 0.7733 | 0.7333 | 0.6000 |
| Qwen3-235B-A22B | gpqa_diamond | 0.7010 | 0.6899 | 0.6778 |
| DeepSeek-R1-0528 | gsm8k | 0.9157 | 0.9154 | 0.9124 |
| DeepSeek-R1-0528 | aime25 | 0.5067 | 0.4934 | 0.4000 |
| DeepSeek-R1-0528 | gpqa_diamond | 0.7707 | 0.7697 | 0.7273 |
| GPT-OSS-120B | gsm8k | 0.9161 | 0.9163 | 0.9152 |
| GPT-OSS-120B | aime25 | 0.7533 | 0.7667 | 0.3533 |
| GPT-OSS-120B | gpqa_diamond | 0.5081 | 0.5434 | 0.3202 |

原文据此观察：在 gsm8k 等较简单数据集上，FP4 与 FP8、BF16 的结果接近；较大模型通常更能容忍 FP4 量化。长上下文中，量化误差(Quantization Error)的累积可能造成更明显的下降。应针对实际模型和工作负载(Workload)评测；较小模型或复杂推理任务可能需要 FP8 或 BF16 才能满足准确率要求。

## 使用建议(Best Practices)

- 优先选择经过离线量化(Offline Quantization)、检查点中包含所需缓存缩放因子的模型。
- 优先考虑 `fp8_e4m3` 的准确率；需要更大动态范围时考虑 `fp8_e5m2`；追求更大显存收益时评估实验性的 `nvfp4` 或 `fp4_mx_block16`，并检查注意力后端兼容性。
